# NUC-004 One-sided is-zero

**Severity:** high · **Default:** on

The classic IsZero bug, carried over from Circom. A hint returns a flag for
"x is zero", and the circuit only checks `x * flag == 0`. That forces
`flag = 0` when `x ≠ 0`, but `flag = 0` also satisfies it when `x = 0`, so
the prover can claim any value is non-zero.

```rust
unconstrained fn is_zero_hint(x: Field) -> Field { if x == 0 { 1 } else { 0 } }

fn is_zero(x: Field) -> Field {
    // Safety: x * flag == 0 below
    let flag = unsafe { is_zero_hint(x) };
    assert(x * flag == 0);
    flag
}
```

## Fix

Also return the inverse and check the other direction:

```rust
let (flag, inv) = unsafe { is_zero_full(x) };
assert(x * inv == 1 - flag);
assert(x * flag == 0);
```

Or compute `x == 0` in constrained code, which the compiler lowers correctly.

Keeping only the other half, `x * inv == 1 - flag`, is just as broken: for
`x ≠ 0` the prover returns `inv = 0`, which forces `flag = 1`, and claims that
`x` is zero. The rule reports both shapes.

## What the rule looks at

A hint whose only constraint (boolean checks on the flag aside) is either
`a * b == 0`, with one factor from the hint and the other not, or
`x * inv + flag == 1`, with `inv` and `flag` from the hint and `x` not.
